## Helper design

The brief names `enf_create`, `enf_setattr` and `enf_lookup_open` as coming
"from the copied memfs harness" in `src/vfs/tests/vfs_enforce_test.c`. They do
not exist there under those names, so they are new code, modelled on that
file's callbacks plus `vfs_acl_sid_test.c`'s `open_child` / `create_file`
sequences. What I chose and why:

**Callbacks lifted verbatim** from `vfs_enforce_test.c`: `wait_done`,
`mount_cb`, `lookup_cb`, `openfh_cb`, `openat_cb`, `setattr_cb`. Same shapes,
same `ctx->done` / `ctx->status` protocol.

**`enf_create(ctx, name, set_attr)`** -- `chimera_vfs_open_at(...,
CHIMERA_VFS_OPEN_CREATE, set_attr, CHIMERA_VFS_ATTR_FH,...)` under a
long-lived `ctx->root_handle` for the `/test` root, then release the new
file's handle. Takes the attrs by pointer so `enf_create_file_with_acl` owns
the freshly built struct (see below).

**`enf_open_root(ctx, name)`** -- lookup + `open_fh` as the SETUP credential.
Factored out because `enf_setattr` and `enf_get_acl` both need it and neither
is the thing under test.

**`enf_setattr(ctx, name, set_attr)`** -- `enf_open_root`, one
`chimera_vfs_setattr`, release. Name-based (not handle-based) so it matches the
brief's call shape and so each setattr is self-contained.

**`enf_lookup_open(ctx, name)`** -- the deliberate asymmetry: the LOOKUP runs
as the setup credential (directory traversal is not what these cases assert),
but the `open_fh` runs as `ctx->cred`. That matters because the open cache
shards handles -- and the per-handle cached access grant -- per credential
(`fh`, `access_mode`, `cred_hash`); opening as anyone else would put the read
on a handle belonging to a different caller. A short comment in the file says
so.

**Setup credential.** The brief suggested `chimera_vfs_get_server_cred()`.
I used an explicit `chimera_vfs_cred_init_unix(&ctx.root, 0, 0, 0, NULL)`
instead. `chimera_vfs_get_server_cred()` returns `getuid()`/`getgid()`, so
under a non-root ctest run it is uid 1001, which is neither root-exempt in the
engine nor the owner of the 7000-owned file -- the ACL setattr would then be
refused for lack of WRITE_ACL and the test would fail for a reason that has
nothing to do with the feature. A literal uid 0 credential is granted
everything by `chimera_acl_access_check` regardless of the host process, and
memfs never impersonates (no `CHIMERA_VFS_CAP_DELEGATES_DAC`), so the setup is
deterministic whether or not the test is run under sudo. This is the one
deviation from the brief's prose and it makes the test stricter about
depending on nothing but the feature.

**`chimera_vfs_read` arity.** The brief's `enf_try_read` calls
`chimera_vfs_read(thread, cred, handle, 0, 1, cb, ctx)`; the real signature
takes `iov`, `niov` and `attrmask` before the callback. Called as
`(..., 0 /*offset*/, 1 /*count*/, NULL, 0, 0, enf_read_cb, ctx)`. memfs
advertises `CHIMERA_VFS_CAP_READ_PROVIDES_BUFFERS`, so a NULL `iov` is correct
there (the core only allocates buffers for backends that do not provide them).
The file is empty, so a granted read returns 0 bytes and no iovecs -- the read
callback asserts `niov == 0` so the test would notice if that ever changed and
started leaking buffers under ASan. The gate runs before dispatch either way,
which is what the assertion is about.

### The three things flagged as easy to get wrong

1. **Borrow contract.** `enf_sids_cb` does `ctx->cred_sids = *sids;` and points
   `ctx->cred.sids` at `ctx->cred_sids` -- a copy into storage `test_ctx` owns,
   never the borrowed pointer. `ctx->cred.sids = NULL` when the resolver
   reports no set. Same rule as Tasks 4 and 5.

2. **`va_acl` lifetime.** `enf_get_acl_cb` `memcpy`s the ACL out inside the
   callback, sized by `chimera_acl_size(attr->va_acl->num_aces)`, and never
   stores the pointer. (For the record: memfs's `memfs_map_attrs` hands out a
   `__thread` scratch copy rather than the live `inode->acl`, but it is still
   only valid through completion, so the rule stands.)

3. **Setattr rebuilds attrs.** `enf_create_file_with_acl` `memset`s and rebuilds
   `struct chimera_vfs_attrs` between the create and the ACL setattr, per the
   brief. Nothing in the file reuses an attrs struct across two calls.

### What makes the cases discriminating

- The file is created owned by 7000/7000 mode 0600, and the caller is
  7001 -- the mode grants it nothing, so any access must come from the DACL.
  (memfs additionally re-derives the mode from the stored ACL, and a SID-only
  ACL projects to 0 permission bits, so the stored mode ends up `S_IFREG|000`.)
- `ENF_USER_GID` (7001) is deliberately left unnameable by the identity
  handler, so the caller's PRIMARY group contributes no SID. `test_mixed_dacl`
  must therefore be granted through its supplementary group SID, not through an
  accidental primary-group match.
- `CHIMERA_ACE_READ_DATA` is not in `ACE_BASELINE` (which is
  `READ_ATTRIBUTES|READ_ACL`) and the caller is not the owner, so
  `test_unresolvable_sid_denies` cannot be granted by implicit rights.

## Concerns for the reviewer

1. **Deviation from the brief (deliberate):** setup uses a literal uid-0
   credential rather than `chimera_vfs_get_server_cred()`. Rationale above --
   the server cred is `getuid()`, which makes the scaffolding fail when ctest
   is not run as root. If you would rather match the brief exactly, the test
   becomes root-only.

2. **`enf_lookup_open` splits creds** (lookup as root, open as the caller).
   Intentional and commented, but worth a reviewer's eye: it means these cases
   say nothing about traversal enforcement, only about the file's own DACL.
   `vfs_enforce_test.c` already covers directory-traversal denial.

3. **Only `test_unresolvable_sid_denies` survives the mutation.** That is by
   construction (it asserts the unchanged fail-closed behaviour), but it does
   mean that single case carries no regression signal for this branch on its
   own. Its value is as the negative control for the other three.

4. **`ACL_BUF` storage alignment.** I kept `vfs_acl_test.c`'s exact macro
   (a `uint8_t` array cast to `struct chimera_acl *`) for consistency with the
   sibling file. The struct's strictest member alignment is 4 and GCC aligns
   local arrays of this size to 16, so this is safe in practice and clean under
   ASan -- but it is technically not guaranteed by the standard. If a reviewer
   wants it hardened, it should be hardened in both files at once, not just
   this one.

5. **`CHIMERA_PRINCIPAL_SID`'s doc comment in `src/vfs/sdk/vfs_acl.h`** still
   says the principal "matches no caller during access evaluation" -- stale
   since Task 1, and now directly contradicted by this test. Out of scope for
   Task 6 (it is a Task 1 file), but it should be fixed before the branch
   merges.
