### `src/vfs/vfs_identity.c`

1. **Includes.** Added `<time.h>` (for `clock_gettime`/`struct timespec`) and
   `<stdio.h>` (for `snprintf`, see the deviations).

2. **`struct chimera_vfs_identity_request`** gained three fields:
   - `inflight_prev` / `inflight_next` -- a second link pair so one job can be on
     `identity->queue` and `identity->inflight` simultaneously. A comment states
     which list owns the default `prev`/`next` at any moment (the queue, a job's
     waiters, or the origin thread's `pending_identity` list -- never two at once).
   - `waiters` -- the head of the list of later resolves that joined this job.

3. **`CHIMERA_VFS_IDENTITY_NEGATIVE_TTL` (60) / `..._BUCKETS` (256)** and
   `struct chimera_vfs_identity_negative`, exactly as the brief specifies.

4. **`struct chimera_vfs_identity`** gained `inflight` (the in-flight job list)
   and `negative[CHIMERA_VFS_IDENTITY_NEGATIVE_BUCKETS]`, both documented as
   guarded by the existing `lock`.

5. **Four new static helpers** (`chimera_vfs_identity_key_eq`,
   `..._negative_hash`, `..._negative_probe`, `..._negative_add`), verbatim from
   the brief apart from the `snprintf` deviation. They are placed immediately
   *before* `chimera_vfs_identity_worker()` rather than before
   `chimera_vfs_identity_resolve()` as the brief's prose says, because the worker
   is defined earlier in the file and calls `..._negative_add`; putting them
   where the brief said would not compile (implicit declaration).

6. **`chimera_vfs_identity_worker()`**: after the handlers run, it takes
   `identity->lock` and, under that one hold, records a negative for a failed
   key, unlinks the job from `inflight` (`DL_DELETE2`), and steals the `waiters`
   list. Outside the lock it fans the result out to each waiter and then hands
   the primary job back to its origin, unchanged.

7. **`chimera_vfs_identity_resolve()`**: the cache-hit fast path is untouched.
   On a miss the request is built first (so the truncated `req->name` is what the
   negative table and the key comparison both see), then under `identity->lock`:
   probe the negative table and complete inline with NULL if it hits; otherwise
   walk `inflight` and, on a key match, append to that job's `waiters` and
   return; otherwise append to both `queue` and `inflight` and signal.

8. **`chimera_vfs_identity_destroy()`**: the queue drain now also unlinks each
   dropped job from `inflight` and frees its `waiters` list, and a new loop frees
   and NULLs every negative bucket.

## The four correctness points

**1. Two link pairs, and not mixing the macros.** `queue` and the `waiters` lists
use the default `prev`/`next`; `inflight` uses `inflight_prev`/`inflight_next`
through `DL_APPEND2` / `DL_DELETE2` / `DL_FOREACH2` exclusively. Every site:

- `resolve`: `DL_APPEND(identity->queue, req)` + `DL_APPEND2(identity->inflight, req, inflight_prev, inflight_next)`;
  `DL_FOREACH2(identity->inflight, inflight, inflight_next)`; `DL_APPEND(inflight->waiters, req)`.
- `worker`: `DL_DELETE(identity->queue, req)` (unchanged) and
  `DL_DELETE2(identity->inflight, req, inflight_prev, inflight_next)`;
  `DL_DELETE(waiters, waiter)` on the stolen waiters head.
- `destroy`: `DL_DELETE(identity->queue, req)` +
  `DL_DELETE2(identity->inflight, req,...)` + `DL_DELETE(req->waiters, waiter)`.

The default pair never has two owners at the same instant: a primary job is on
`queue` until the worker pops it, is on no `prev`/`next` list while the handlers
run, and is put on `origin->pending_identity` afterwards; a waiter is only on its
job's `waiters` list and then on its own origin's `pending_identity`. The struct
comment records this so a later reader does not add a third use of `prev`/`next`.

**2. Every waiter resumes on its own origin thread.** The fan-out reads
`origin = waiter->origin` for each waiter and appends to *that* thread's
`pending_identity`, ringing *that* thread's doorbell -- the primary's origin is
never used for a waiter. The result is copied per waiter
(`waiter->found = req->found; waiter->result = req->result;`), before the append,
because the waiter is freed by whichever thread drains it, concurrently with the
primary being drained elsewhere; sharing a pointer into `req` would be a
cross-thread use-after-free.

**3. Every `..._negative_probe()` caller holds `identity->lock`.** The probe
mutates the table (it unlinks and frees expired entries as it walks), so this is
not optional. There are exactly two callers:
- `chimera_vfs_identity_resolve()`, between its `pthread_mutex_lock(&identity->lock)`
  and the matching unlock on every path out (negative hit, join, queue).
- `chimera_vfs_identity_negative_add()`, which is documented "Caller holds
  identity->lock" and has exactly one caller: the worker, inside the critical
  section it takes after the handlers return.
No third call site exists (`grep -c negative_probe` -> the definition plus those
two). The helpers never take the lock themselves, so the nesting is flat and
there is no recursive-lock hazard.

**4. A job leaves `inflight` before its waiters are detached, and nothing joins
afterwards.** Both happen under one uninterrupted hold of `identity->lock`:

```c
        pthread_mutex_lock(&identity->lock);
        if (!req->found) {...negative_add... }
        DL_DELETE2(identity->inflight, req, inflight_prev, inflight_next);
        waiters      = req->waiters;
        req->waiters = NULL;
        pthread_mutex_unlock(&identity->lock);
```

A resolve can only join by finding the job while walking `inflight` under the
same lock, so it either wins the race (joins before the delete, and is in the
`waiters` the worker then steals) or loses it (the job is already gone from
`inflight`; it falls through and, because the negative was recorded in the same
critical section, is answered by the negative cache or queues a fresh job for a
key that resolved into the user cache). A waiter can never be appended to a list
nobody will ever hand results to. The negative is added *before* the delete, in
the same section, precisely so the losing resolve has an answer to find.

## The shutdown teardown (brief Step 7, code not supplied)

Brief-supplied part -- free the negative table:

```c
    for (b = 0; b < CHIMERA_VFS_IDENTITY_NEGATIVE_BUCKETS; b++) {
        neg = identity->negative[b];
        while (neg) {
            neg_next = neg->next;
            free(neg);
            neg = neg_next;
        }
        identity->negative[b] = NULL;
    }
```

(with `neg`, `neg_next` and `b` added to the function's locals, since chimera
declares locals at the top of the function).

Prose-only part -- free each dropped job's waiters, which is required or ASan
reports the leak at teardown:

```c
    /* Any jobs still queued at shutdown are dropped (their callers are gone),
     * and with them anything that joined them: a waiter is owned by the job it
     * is parked on, so nothing else would ever free it. */
    while (identity->queue) {
        req = identity->queue;
        DL_DELETE(identity->queue, req);
        DL_DELETE2(identity->inflight, req, inflight_prev, inflight_next);

        while (req->waiters) {
            waiter = req->waiters;
            DL_DELETE(req->waiters, waiter);
            free(waiter);
        }

        free(req);
    }
```

The `DL_DELETE2` there is mine, beyond what the brief asked. Every queued job is
on `inflight` too (both appends happen under one lock in `resolve`), so freeing
it while leaving it linked into `inflight` would leave the head pointing at freed
memory. Unlinking keeps the two lists consistent for the whole of `destroy` and
costs nothing. This loop is normally empty: the workers only exit once
`shutdown && !queue`, so they drain the queue themselves; it fires only for a
resolve issued after shutdown was signalled.

## Deviations from the brief

1. **`snprintf` instead of `strncpy` in `..._negative_add`.** The brief's
   `strncpy(neg->name, name, sizeof(neg->name) - 1)` fails the Release build:

   ```
   src/vfs/vfs_identity.c:365:9: error: '__builtin_strncpy' output may be truncated
   copying 255 bytes from a string of length 255 [-Werror=stringop-truncation]
   ```

   The caller passes `req->name`, a fixed-size array, so gcc knows the source's
   maximum length and rejects the copy. (The identical `strncpy` in `resolve()`
   is fine because its source is an unbounded `const char *`.) Replaced with
   `snprintf(neg->name, sizeof(neg->name), "%s", name)`, which truncates
   identically and always NUL-terminates, with a comment saying why. This is why
   `<stdio.h>` was added. Debug alone would not have caught this -- it is
   Release's `-O3 -Werror` only.

2. **Helpers placed before the worker, not before `resolve()`.** Explained above:
   `..._negative_add` is called from the worker, which is defined first.

3. **The counting-handler state is `static` in each test function.** The brief
   has `struct counting_handler_state st` as a plain local, whose address is
   handed to `chimera_vfs_identity_register_handler()`. Handlers are never
   unregistered, so after `test_negative_cache()` returns, the resolver still
   holds a pointer into its dead frame -- and `test_inflight_dedup()` then
   resolves a key that runs every handler, including that one, which does
   `__sync_fetch_and_add` through the dangling pointer from a worker thread.
   Making the state `static` (same names, same assertions) removes the
   stack-use-after-return without changing what the tests prove. A comment in the
   file records the reason.

4. **The header doc comment**, described above. The brief did not mention it; the
   contract it states became inaccurate, and Task 3 reads it.

Also worth noting, though not a deviation: the worker's waiter fan-out reads
`origin` out of the waiter *before* the append publishes it. The brief's Step 6
code reaches through `waiter->origin` for the doorbell after the append, which is
exactly the use-after-free that commit `d1ee0231` ("vfs: read the origin before
publishing an identity job to it") fixed for the primary job one commit ago. The
committed fan-out follows the fixed pattern.

## Concerns for the reviewer

1. **Negative-table sweeping is passive.** Expired entries are dropped only when
   a probe walks their bucket. A burst of distinct unresolvable keys followed by
   silence leaves those entries allocated until the next probe hashes into the
   same bucket (or until `destroy`). It is bounded by the number of distinct keys
   asked for, each entry is ~280 bytes, and the miss path is the only thing that
   grows it -- but there is no cap and no eviction other than the TTL. A bound
   (entries per bucket, or a total count) would be cheap to add if the reviewer
   wants one; I left it out because the brief specified the structure exactly and
   an unbounded-but-TTL'd table matches the user cache's own behaviour.

2. **The in-flight scan is a linear walk under the resolver lock.** Its length is
   the number of distinct keys currently being resolved (bounded in practice by
   the worker count plus whatever is queued), and `resolve` only reaches it on a
   cache miss. If a future caller fans out hundreds of distinct uncached SIDs at
   once -- which is roughly what Task 3's per-caller SID set could do on a large
   ACL -- this becomes O(n^2) under a lock held by every missing resolve. Worth
   keeping in mind when Task 3 lands; a hash keyed like the negative table would
   be the fix, and the key-matching helper is already shared.

3. **Key truncation.** `key_eq` compares the request's truncated `name` (256
   bytes; SIDs cap at `CHIMERA_VFS_SID_MAX_LEN` = 80, so only usernames could
   reach it). Two usernames sharing a 255-byte prefix would be treated as one key
   by both the negative table and the in-flight join. The request struct already
   truncated names the same way before this change, so no new exposure, but the
   consequence is now "wrong identity coalesced" rather than "wrong string passed
   to a handler".
