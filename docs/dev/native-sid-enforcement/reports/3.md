## 3. Verifying the all-inline completion path (decision 2)

The parent flagged this as the case that matters most now that Task 2 makes
inline completion common. I verified it two ways.

### 3a. A test that exercises it

`test_all_inline_completion` uses credential `(uid 4998, gid 4998, ngids 0)`,
which no registered handler names:

1. First resolve: cold, parks, and comes back with `sids == NULL` -- the set is
   empty, so `_decr()` reports "no set at all". Crucially the entry is left
   **invalid**, so the warm shortcut at the top of
   `chimera_vfs_cred_resolve_sids()` does *not* apply to it.
2. Second resolve of the same credential: both identities (BY_UID 4998,
   BY_GID 4998) are now in the identity layer's negative cache, so
   `chimera_vfs_identity_resolve()` fires both callbacks INLINE. The test
   asserts `again.done` with no `evpl_continue()` at all -- i.e. the whole
   resolve completed synchronously inside the call.

This is precisely the shape decision 2 describes, and it is reached through the
cold path (allocation, fan-out, join), not the one-line warm shortcut. The
brief's own warm case (`warm.done` in `test_resolve_and_cache`) exercises the
warm shortcut instead, which never allocates a ctx -- so it would *not* have
caught a broken guard.

The test is robust to host variation: if some host's NSS did resolve uid 4998,
the identities land in the *positive* cache instead and the second resolve is
still all-inline; and since NSS never supplies a SID string the set is still
empty, so the entry is still invalid and the cold path is still taken.

## 4. Deviation from the brief: `inflight` on the cache entry

**This is the one place I did not follow the brief literally, and the reviewer
should decide whether to keep it.**

The parent asked me to check whether the stated justification for the LRU-style
reuse holds. The stated justification is:

> no second resolve can start on this thread while another resolve's callback
> is running

That part is true -- `chimera_vfs_identity_thread_complete()` drains its job
list serially on the owning evpl thread, so callbacks do run to completion. But
it is not the property the reuse actually needs. The reuse needs:

> no second resolve can start while another resolve is **in flight**

and that is false. A parked resolve sits on a worker for the whole round trip,
and the evpl loop keeps running other work meanwhile. Two SMB session setups
landing on the same VFS thread is the ordinary case, not a corner.

The concrete failure with the brief's code as written:

1. Resolve A for hash `H_A` is parked. Its entry `E_A` is the tail of bucket
   `b`, and `ctx_A->entry == E_A`.
2. Resolve B starts for a different credential with hash `H_B`, `H_B % 64 == b`.
   The bucket already holds 4 entries, so `intern()` takes the tail -- `E_A` --
   `memset`s it and stamps `E_A->hash = H_B`.
3. Resolve A's lookups complete and write **credential A's** user and group SIDs
   into `E_A->sids`, and `_decr()` sets `E_A->valid = 1`.
4. `E_A->hash` is now `H_B`. A later `chimera_vfs_cred_sids_lookup()` for
   credential B returns credential A's SID set.

That is not a crash (the entry is reused, never freed, so there is no
use-after-free) -- it is an identity mix-up in a structure whose entire purpose
is authorization, which is worse. B is evaluated against A's group SIDs.

The fix is small and local: an `inflight` counter on the entry, incremented in
`chimera_vfs_cred_resolve_sids()` before the lookups are issued and decremented
in `_decr()`. `intern()` then picks as its victim the last entry in the chain
with `inflight == 0`, repurposing it in place (its `next` is saved across the
`memset` so the chain is not truncated -- the brief's version only worked
because it always picked the tail, whose `next` is `NULL`). If every entry in
the chain is in flight there is no victim and a new entry is allocated, so the
chain transiently exceeds `CHIMERA_VFS_CRED_SIDS_CHAIN` rather than corrupting
anything; it returns to the bound as soon as those resolves finish.

The same counter also fixes a second, milder version of the problem: two
resolves of the **same** credential overlapping. The brief unconditionally
`memset`s the entry at the start of every cold resolve, so the second one would
wipe the SIDs the first had already collected. With the counter,
`chimera_vfs_cred_resolve_sids()` only resets an entry with `inflight == 0`;
otherwise it joins in place, which is safe because both resolves write the same
slots from the same ids (idempotent).

Cost: 4 bytes per entry (it fits in the existing padding after `int valid`) and
one comparison per chain walk on insert only. The warm path, the `_lookup()`
path and the borrow contract are all untouched.

## 5. Where thread teardown is hooked

`grep -n "chimera_vfs_thread_destroy" src/vfs/vfs.c` gives three hits: two call
sites (the delegation thread at :157 and the close thread at :367) and the
definition at :1259. I added the call inside the definition, in

and before the `free_find_results` / `free_synth_handles` / `free_requests`
drains -- i.e. grouped with the other per-thread frees, and well before the
`free(thread)` at the end.

Placing it after the module loop rather than before is deliberate: a backend's
`thread_destroy` could in principle still consult the thread's credential state,
and nothing in the resolver depends on module teardown ordering.

which calls `chimera_vfs_thread_destroy()` after having interned four distinct
credentials (uid 4100 with 2 gids, uid 4100 with 1 gid, uid 4998, and the

## 7. Concerns for the reviewer

**1. The `inflight` deviation (section 4) -- please confirm or reject.** It is
the only place I departed from the brief. I judged that shipping a known
cross-credential SID mix-up in an authorization cache was worse than the churn,
but the call is the reviewer's. Backing it out is mechanical: drop the field,
drop the `if (entry->inflight == 0)` conditions in
`chimera_vfs_cred_resolve_sids()` and `intern()`, and restore the brief's
tail-eviction. I did **not** write a regression test for it -- constructing it
needs five credentials colliding into one bucket while a sixth resolve is
parked, which means hardcoding `CHIMERA_VFS_CRED_SIDS_BUCKETS` (a private
constant) in the test. That felt more fragile than valuable; say the word if you
want it.

**2. The borrow contract is honoured for the documented usage, but its wording
is very slightly stronger than the code guarantees.** The header says a borrowed
set is "valid until the calling thread returns to its event loop". A set handed
to a callback is certainly valid for that callback's duration. But if code
*inside* that callback (or later in the same loop turn) starts a resolve for a
different credential that hashes to the same bucket, and that bucket is full,
`intern()` may repurpose the very entry just handed out. So the true guarantee
is "valid until this thread starts another cold resolve". This costs nothing for
the planned consumers -- Task 4 copies the set immediately, Task 6 uses it for a
single ACL evaluation -- and closing it properly needs a loop epoch to mark
entries borrowed this turn, which felt disproportionate here. Flagging it so
Tasks 4 and 6 do not lean on the stronger reading.

**3. A hash collision between two genuinely different credentials returns the
wrong SID set.** `chimera_vfs_cred_sids_find()` compares `hash` only -- it does
not re-verify uid/gid/gids. `chimera_vfs_cred_hash()`'s own doc note argues a
collision is acceptable because the worst case is "sharing an open handle, no
security boundary under AUTH_SYS". That reasoning does not transfer cleanly to
SIDs, where a collision means evaluating caller X against caller Y's group SIDs.
This is inherited from the brief's design rather than introduced by me, and at
64 bits it is vanishingly unlikely, but it is a different risk profile from the
one the hash's doc comment signed off on. Storing uid/gid/ngids on the entry and
comparing them on a hash match would close it for a few bytes.

**4. Overlapping resolves of the same credential can under-report once.** With
the `inflight` join, if resolve #1 and #2 are both in flight on one credential,
#1 completes against whatever slots are filled at that moment. If that is none,
#1's caller sees `NULL` and is evaluated without its SIDs, while #2 sees the
full set moments later. The failure direction is safe (access denied, not
wrongly granted) and self-correcting on the next request. Worth knowing when
reading Task 4's session-setup path.

**5. `chimera_vfs_cred_sids_warm()` swallows failures silently by design.** It
is fire-and-forget with an empty callback, so a credential that never resolves
just never populates the cache and every `_lookup()` for it keeps missing --
re-resolving on each warm call, with the identity negative cache (60 s) as the
only backstop. That matches the brief's intent ("proceed unresolved once, and
are enforced from the next request on"), but a caller that warms per request on
a permanently-unresolvable credential pays a cache probe plus a fan-out every
time. Task 5 should warm at most once per credential per request, not per
operation.

# Fix report: review round 1

**Fix commit:** `fed8ea9e` -- `vfs: hold a borrowed SID set across its callback`
(3 files changed, 383 insertions, 30 deletions)

All three Important findings addressed, plus the eviction coverage the
coordinator promoted from Minor. The `inflight` deviation is kept, as ruled.

The reviewer's sharpening of the eviction analysis is correct and worth
recording: once a bucket saturates, the brief's `intern()` hands the same tail
to every subsequent cold resolve, so a parked entry in a full bucket is the
victim *every* time rather than occasionally. That moves the original finding
from "unlikely race" to "deterministic once the bucket fills".

## Important 1 -- pin held across the callback

`chimera_vfs_cred_sids_decr()` now drops `entry->inflight` *after*
`callback(...)` returns, not before. The comment at the drop states why.

While fixing it I found the **same hole in a second place the review did not
name**: the warm shortcut in `chimera_vfs_cred_resolve_sids()` hands out
`&entry->sids` without touching `inflight` at all, so a callback reached that
way was never pinned either. That path is the common one (every repeat caller),
and it would have made the header's new "pinned for the duration of the
callback" promise false for most callbacks. It is now bracketed:

```c
    if (entry && entry->valid) {
        entry->inflight++;
        callback(&entry->sids, private_data);
        entry->inflight--;
        return;
    }
```

The eviction comment in `intern()` was rewritten as instructed: it no longer
leads with the single-threaded-callback property. It now states the invariant
purely in terms of `inflight` (non-zero = a resolve holds it by pointer, or a
callback is reading the set it was handed; zero = nothing holds it), and
explicitly records that the property the brief relied on does **not** imply it,
because a parked resolve spans many trips round the loop.

## Important 2 -- exact credential key

`struct chimera_vfs_cred_sids_entry` now carries `flavor`, `uid`, `gid`,
`ngids` and a `gids[CHIMERA_VFS_CRED_MAX_GIDS]` prefix -- every field
`chimera_vfs_cred_hash()` mixes. Two new helpers,
`chimera_vfs_cred_sids_key_eq()` and `chimera_vfs_cred_sids_set_key()`, compare
and stamp them. `chimera_vfs_cred_sids_find()` and
`chimera_vfs_cred_sids_intern()` both take the `cred` now; the hash only selects
a candidate and the key decides.

This closes the reviewer's (a) and (b) together. The join-in-place at the top of
the cold path can now only join an entry for *the same credential*, because
`find()` proved every field equal, so both the shared-`entry->sids` merge and
the `ngroups`-of-one-credential / `gids[]`-of-another overrun are unreachable by
construction rather than by luck. The comment above the join says so.

One consequence worth flagging: `find()` previously tolerated a NULL `cred`
(via `chimera_vfs_cred_hash(NULL)`, which is defined) because it only compared
hashes; `key_eq()` would dereference it. `find()` therefore returns NULL early
for a NULL cred. This is not new behaviour -- `chimera_vfs_cred_resolve_sids()`
already dereferences `cred->ngids`, so nothing is ever interned for a NULL cred
and there was never anything to find -- it just avoids introducing a crash where
the old code happened not to have one.

## Important 3 -- header now matches the code

I weakened the wording rather than adding pinning to `_lookup()`, because
pinning there would need a matching release call and Tasks 4 and 6 are being
written against this API right now. The header states the two cases separately:
a callback's set is pinned for the callback's duration (true on both hand-out
paths after Important 1); a `_lookup()` set is pinned by nothing and is valid
only until this thread's next `chimera_vfs_cred_resolve_sids()` /
`chimera_vfs_cred_sids_warm()`, and never past the current trip through the
event loop. `chimera_vfs_cred_sids_lookup()`'s own comment repeats the bound,
and `chimera_vfs_cred_resolve_sids()`'s mentions the pin.

## New test coverage

Two cases added to `src/vfs/tests/vfs_cred_sids_test.c`.

**`test_eviction_keeps_entries_honest`** -- the probabilistic sweep the reviewer
described. 400 credentials, each with its own user and group SID from a
dedicated handler; every resolve must answer with its own SIDs, then a second
sweep demands every `_lookup()` either miss or return that credential's set. It
asserts `cached < 400` so the sweep cannot silently stop forcing eviction. No
private constants are hardcoded. Actual: **the cache kept 52 of 400**, so ~348
evictions ran.

**`test_borrow_pinned_across_callback`** -- added because the eviction sweep
does *not* cover Important 1 (verified below: the mutation passes it). 300
credentials, each resolved twice -- once cold, so the set arrives from the
fan-out join, and once warm, so it arrives from the shortcut -- and each
callback resolves an unrelated credential before re-reading the set it was
handed. The nested credential is one nothing names, so it interns an entry (the
eviction pressure) and parks; `intern()` memsets its victim before issuing any
lookup, so the clobber does not depend on the nested resolve completing. The
nested resolves are counted and drained so nothing is left parked at teardown.

## Concerns after this round

1. **Important 2 is unproven at runtime** (see the mutation table). Sound by
   construction, but if you want a test the only practical route is a build-time
   seam for a weak hash.

2. **The chain bound is now soft.** When every entry in a bucket is pinned,
   `intern()` allocates rather than evicting, so a bucket can exceed
   `CHIMERA_VFS_CRED_SIDS_CHAIN` while resolves are outstanding. It shrinks back
   as they finish, and each entry is ~1.4 KB. Bounded in practice by the number
   of credentials concurrently resolving on one thread, which is small -- but it
   is a bound by argument, not by construction.

3. **The entry grew.** It now carries 80 bytes of credential key on top of the
   ~1.3 KB SID set, so the whole cache is roughly 256 x 1.4 KB = 360 KB per VFS
   thread at full occupancy. Fine for a handful of threads; worth a glance if
   the thread count is ever large.

4. **Deferred Minors untouched**, as instructed.
